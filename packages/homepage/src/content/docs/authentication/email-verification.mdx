---
title: Email Verification
description: Configure email verification for user registration
---

Email verification ensures users provide valid email addresses during registration. This prevents fake accounts and enables secure password recovery.

## Configuration

Email verification is controlled per authentication method:

```yaml
basic_authentication_methods:
  password:
    enabled: true
    email_verification: true
  passkey:
    enabled: true
    email_verification: true
```

## Requirements

Email verification requires SMTP configuration:

```yaml
smtp:
  host: smtp.example.com
  port: 587
  secure: true
  user: noreply@example.com
  password: !env SMTP_PASSWORD
  from: noreply@example.com
```

## Verification Flow

### Password Registration

```
User Submits Registration
          │
          ▼
Account Created (unverified)
          │
          ▼
Verification Email Sent
          │
          ▼
User Clicks Link
          │
          ▼
Email Verified ──► Login Allowed
```

### Passkey Registration

When using passkey authentication with email verification:

1. User enters email address
2. Verification email is sent
3. User clicks verification link
4. User is prompted to create passkey
5. Account is created and verified

## API Endpoints

### Verify Email

```http
POST /api/v1/auth/email/verify
Content-Type: application/json

{
  "token": "verification-token-from-email"
}
```

### Resend Verification Email

```http
POST /api/v1/auth/email/resend
Content-Type: application/json

{
  "email": "user@example.com"
}
```

## Email Content

The verification email contains:

- Link to verify the email address
- Expiration notice (typically 24 hours)
- Instructions for the user

Example email:
```
Subject: Verify your email address

Hello,

Please click the link below to verify your email address:

https://auth.example.com/verify?token=abc123...

This link will expire in 24 hours.

If you didn't create an account, you can safely ignore this email.
```

## Token Expiration

Verification tokens expire after a configurable period:

- Default: 24 hours
- Single-use: Token is invalidated after verification

## Unverified User Behavior

When a user hasn't verified their email:

1. **Login**: Blocked with "Email not verified" message
2. **Password Reset**: Still available (helps users who lost verification email)
3. **Resend**: Users can request a new verification email

## Disabling Email Verification

For development or internal applications:

```yaml
basic_authentication_methods:
  password:
    enabled: true
    email_verification: false
```

:::caution
**Security Warning**: Disabling email verification allows:
- Fake email addresses
- Account squatting
- No password recovery (without valid email)

Only disable in trusted environments.
:::

## Development Mode

For local development without SMTP:

```yaml
smtp:
  test: true  # Logs emails to console

basic_authentication_methods:
  password:
    enabled: true
    email_verification: true
```

In test mode, verification tokens are logged to the console.

## Best Practices

1. **Always enable in production** - Verify user emails
2. **Configure SMTP properly** - Test email delivery
3. **Provide resend option** - Users may miss initial email
4. **Set reasonable expiration** - 24 hours is typical
5. **Clear error messages** - Help users understand the process

## Troubleshooting

### Verification Email Not Received

1. Check spam/junk folder
2. Verify SMTP configuration
3. Check email address spelling
4. Review SMTP server logs
5. Ensure sender domain has proper SPF/DKIM records

### Token Expired

Users can request a new verification email via the resend endpoint.

### Already Verified

If a user tries to verify an already-verified email, show a friendly message directing them to login.

## Customizing Email Templates

Email templates can be customized in the backend. The default templates are located in the email service and support localization based on user preferences.
